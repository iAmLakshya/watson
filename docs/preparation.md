Watson's pre-call preparation scheduler combines calendar attendees with saved people, completed meeting history and permitted CRM facts, then performs public participant/company research through configured OpenAI web search. It runs without starting capture or recording and excludes active sessions, transcripts, screenshots, microphone data, and hidden prompt bodies from its preparation input.

Automatic preparation is disabled initially. The settings are `automaticPreparation`, `preparationLeadMinutes` (1–180 minutes, default 15), `preparationRefreshMinutes` (5–1,440 minutes, default 60), and an optional `preparationModel` that otherwise uses the current configured model. The scheduler checks upcoming events every 30 seconds, prepares at most three per tick, and considers the nearest events within its bounded cache capacity. `calendar:prepare` accepts `{eventId,force?}` for an explicit request; `calendar:prepare-cancel` accepts `{eventId?}`. Turning automatic preparation off aborts its active automatic request and stops the remaining batch. Explicit manual preparation remains available.

Participant fields come from actual calendar metadata or a unique exact-email match to a saved person. A supplied name can be researched even when its email uses Gmail, Outlook or another personal mailbox and the company is unknown. Public results remain unknowns or explicitly labelled candidates when identity or affiliation cannot be confirmed; they do not become verified attendee identity. Company and role fields are copied only from the supplied saved-person record and never filled from generated name matches. An email domain is identified as a domain, never proof of employment. Consumer mailbox domains do not become employers. Duplicate saved-email matches remain ambiguous, with no saved person selected; a supplied calendar name remains a public lookup clue. Email-only personal addresses with no name or company context retain `setup_required` and empty generated text. Research does not create or modify Person records.

The default provider uses the configured model at the official Responses endpoint with `web_search`, required tool execution, `store:false`, a bounded output budget and requested source metadata. A completed response must contain an executed web search and valid URL citations. Citation annotations become clickable Markdown links; unsafe URL schemes and responses without usable citations are rejected. A managed organization adapter can instead use the existing authenticated assistant, with actual operator readiness and returned web sources. It cannot substitute a fake local API key. [OpenAI web search and citation documentation](https://developers.openai.com/api/docs/guides/tools-web-search)

Preparation preserves the difference between calendar or user-maintained facts and sourced public research. The prompt instructs the model to report unknown affiliations, avoid merging same-name people and avoid searching private notes or commitments. Calendar, people, history and CRM source references accompany the resulting brief. Source links are returned by the provider; Watson does not invent researched profile fields or citation URLs. Factual accuracy and identity ambiguity in a live provider answer still require review of its linked sources.

The cache stores at most 50 event entries by default, supports a programmatic limit of 1–100, and expires briefs using the configured refresh period. It persists atomically to the supplied cache path with private file permissions. Calendar metadata, relevant people/history/CRM facts, model, language and the account/access/provider scope produce the cache fingerprint. Changed or revoked context clears the old result synchronously and aborts affected research; late responses are discarded. Deleted events and events ended more than a day ago are removed. The desktop must include account, access scope and selected provider or mode in `contextScope`; automatic preparation results should remain in this cache rather than being copied into the legacy calendar `briefing` field.

Each request has a 45-second timeout. Network, provider availability and rate errors have at most three automatic attempts with bounded backoff; authentication failures wait for a credential/readiness change or explicit retry. Missing key, missing model and insufficient participant detail produce specific setup states and never a fixture briefing. Cancellation, error, setup and ready statuses are exposed per event. No provider credential enters the preparation cache or renderer state. Shutdown cancels and drains a live request.

[preparation.test.ts](../tests/preparation.test.ts) uses a real local HTTP Responses fixture and synthetic records. It verifies required web requests and actual citation parsing, unique identity matching, automatic research of supplied full names with personal emails and sourced unknown/candidate results, email-only setup gates, no transcript/capture inputs, lead-time opt-in behavior, persistence and bounded cache, deleted events, context revocation and discarded late answers, key/model/identity setup gates, rate retry bounds, managed readiness without fake keys, credential recovery, later-event scheduling, and disabling automatic research. Live OpenAI calls with customer data were not performed during implementation. Engine, IPC and rendered Calendar integration are validated separately by their owning modules.
