# Watson desktop cloud connection

Watson’s desktop process connects to the included server over HTTP on loopback or HTTPS remotely. Authentication, revision sync, sharing and organization permissions use the real SQLite backend in `server/src/app.ts`. This is a working client/server implementation; it is not evidence of a hosted deployment or of live identity, billing or AI provider credentials.

## Desktop use

Start the backend with the commands in `server/README.md`. In Watson, open Settings → Sync & sharing, save the server address, and create an account or sign in. The default address is `http://127.0.0.1:4319`. Sign-in requires the operating system’s credential encryption service.

No background upload runs. Select individual sessions, knowledge documents, modes, calendar events, people, scorecards or folders and choose Review uploads. The review names the account, endpoint and records before Upload & sync sends them. Download updates sends no newly selected personal records. An interrupted, previously confirmed upload requires another explicit review before retry. Discard queued uploads removes a rejected or unwanted local queue while preserving notes and any server copy that may already have arrived. Local deletions appear as selectable server deletions for records already linked to the account. Folder uploads are ordered before their descendants, knowledge documents before modes, and dependency cycles are rejected before the queue is changed.

Sessions sync notes, transcript, assistant answers, actions, follow-up drafts, attendees, commitments, coaching and measured usage. Modes retain instructions, note/email templates, custom actions and document references. Provider credentials, encrypted keys, environment credentials, bearer tokens, screen exclusion, device selection, capture toggles, OS permissions, launch behavior and shortcut preferences never enter workspace sync payloads. Only theme, language, output language, model choices, instructions, Smart mode, its independent model/reasoning/web-search/output-budget preferences and the active personal mode preference can sync from settings. Screen images and audio bytes are excluded from ordinary workspace sync. [Private audio attachments](cloud-recordings.md) use a separate, explicitly approved streaming upload.

## Accounts, concurrency and persistence

`electron/cloud-client.ts` stores connection state in a separate `cloud.json` beside Watson’s local data. The opaque bearer token is encrypted by the supplied OS secret storage. Its plaintext and ciphertext are absent from `CloudStatus` and renderer IPC replies. Passwords are used for the request only. TLS credentials are never sent after a redirect: requests use `redirect: 'error'`. Remote HTTP endpoints and embedded URL credentials are rejected.

Revision cursors, bases, pending mutation IDs and conflict copies are isolated by server endpoint and account ID. Signing into another account selects no local records for upload. An incoming record that collides with an unbound local ID creates a conflict instead of replacing the local record. Existing account queues remain scoped to that account; they cannot be sent while another account is active.

Signed operations capture their account, endpoint and device when invoked. If another queued action signs into a different account before they execute, the original operations fail before sending any HTTP request or applying local changes. This also protects approved sync, sharing, organization/connector mutations, account edits, analytics and conflict resolution. Intentionally public sign-in, server configuration and password-recovery flows keep their own behavior; same-actor retries remain valid.

Sync compares the remote revision against the last accepted base. The server enforces `expectedRevision`; durable `changeId` values make a retry after a lost response idempotent. If local and remote copies changed, the local copy remains untouched and both copies appear in review. Use server replaces the local copy, Keep local queues it against the observed server revision for the next explicitly reviewed upload, and Keep both saves a new local copy before applying the server copy. A later competing server edit can produce another conflict; there is no unconditional overwrite path.

`electron/cloud-store.ts` validates and normalizes a complete remote batch into a cloned workspace before saving it. Invalid data leaves the previous workspace unchanged. A failed save restores the original in-memory workspace. The application rejects applying remote changes while live capture or generation is active. Revision bases and callback payloads are separate deep copies, so editing downloaded notes cannot mutate the synchronization baseline. Recursive payload normalization omits undefined object fields and converts undefined or sparse array entries to JSON null; optional fields inserted by the local adapter therefore compare against the actual server wire representation, allowing rich sessions to be shared immediately after their first upload.

## Shares and organization context

Public links require a synced session without unresolved changes. The client displays the actual `viewerUrl` returned by the server, preserves its JSON API URL separately, and supports expiry and revocation. The HTML viewer escapes note content and displays notes, actions, follow-up and transcript. Local server URLs are reachable on that machine; remote sharing needs a reachable HTTPS endpoint. Opening a share uses the main process’s scoped `cloud:open-share` command, which opens only a saved share URL belonging to the configured server. Generic links and custom actions retain their HTTPS rule.

Organization controls operate on backend membership, team, shared-resource, policy, usage and audit endpoints. Memberships require accounts that already exist on the server. Permissions and final-admin protections are enforced server-side. Publishing copies selected local content to an explicitly chosen organization or team scope. Shared documents, modes and scorecards are normalized as read-only context with namespaced IDs and stay separate from personal storage.

Mode assignment is explicit: an administrator or authorized team manager assigns one mode per member, replacing any previous assignment. `sync.assignedMode` is separate from the management resource listing. Members receive a mode’s name and action labels with `inference: 'server'`; private instructions, templates, document references and custom action bodies stay on the server. Assigned requests use the authenticated `/assistant` streaming gateway with the operator’s model and key. Managed links resolve through `/assistant/action-link` without exposing their URL templates. There is no fallback to an empty or locally reconstructed hidden prompt. Unconfigured inference and Smart research return explicit setup errors. Coaching requires an accessible synced scorecard. Personal modes can reference authorized shared documents: the client converts namespaced desktop references into server IDs on upload and restores the namespace on download.

Managed Smart reports the operator's separate Smart model, reasoning effort, output budget, compatibility and web policy through safe status fields. Deep Smart forwards an independent web-search preference; sourced calendar research uses an explicit research-only intent and the operator's research model without a reasoning override. Member-supplied model, instructions, keys or token budgets do not cross this client request boundary. Canonical provider refusals become a controlled generic decline with `refused: true`; that flag survives workspace sync and lets generation consumers preserve existing notes, email, preparation and coaching instead of treating a decline as new facts.

The enterprise panel checks actual server configuration for OIDC sign-in, SCIM directory provisioning and Stripe billing. OIDC start keeps the one-time request secret in the main process; the renderer receives only the browser URL and expiry. Billing opens a server-created secure checkout or customer portal, with prices reviewed on checkout. SCIM metadata displays its organization endpoint; provisioning credentials are managed on the server and are not exported as shared content. Live provider setup and paid transactions remain unverified without the corresponding service configuration.

The typed `cloud:connector` command maps fixed Google Calendar, Merge CRM/ATS, approved knowledge URL, field mapping, contact matching and writeback operations. It does not expose an arbitrary route proxy. Google sync, calendar selection and disconnect reconcile imported calendar resources and tombstones using a download-only revision request. They never submit pending personal uploads. CRM facts become read-only context; importing a chosen contact into People is a separate explicit action. Account and provider tokens are submitted once to encrypted server storage, never saved in cloud profile state or returned to the renderer. Merge linking retains its exchange state privately in the main process and returns only the hosted browser URL and expiry. Writeback requires a synced meeting, exact preview, explicit confirmation and a stable idempotency key. The preview includes an opaque review capability that expires after ten minutes; it is bound to the author, connection, destination and reviewed notes/title/actions. This review capability is deliberately returned for the approval flow and is separate from provider authentication tokens. Enqueue rejects changed content, invalid/expired reviews and mismatched authors before creating any jobs. Matching retries retain their original token and job key. Classified `preview_required`, `preview_changed` and `preview_invalid` failures require a new review; network failures preserve the same pending approval so an uncertain response does not create a fresh write key. The client exposes persisted job status and the server’s deliberate duplicate-risk retry gate. Refresh replaces cached connector facts and assignments with the current account’s ACL-filtered view.

## Evidence and verification

Run `node --import tsx --test tests/cloud-client.test.ts tests/cloud-store.test.ts tests/cloud-analytics-client.test.ts tests/cloud-auth-client.test.ts tests/cloud-recordings-client.test.ts` for the client integration gate. The executed 32-test gate uses the desktop client and store adapter against a real HTTP server and temporary SQLite databases, covering encrypted sign-in state, selective uploads, local capture protection, concurrency conflicts, account switching, queued approval invalidation, idempotent network retries, account changes/deletion, HTML share links/revocation and organization ACLs. It also traverses the actual OIDC handoff and assigned-inference gateway to local provider fixtures, tests independent managed Smart web/research intent and refusal history, and imports Google calendars and Merge contacts, removes deselected events, preserves credential boundaries and runs explicitly approved CRM writeback jobs. Store tests cover normalization, invalid-batch rollback, persistence failure, tombstones, citation IDs, scorecard constraints and read-only shared context. Audio fixtures stream more than 5 MiB, verify the exported SHA-256 and exact bytes, refresh meeting revisions, check public/foreign exclusion and reject queued actor changes before file or network access. These tests use an AES secret-storage fixture; OS credential storage and native chooser/save-dialog behavior need the packaged runtime checks. The backend’s `server/tests` separately verifies the wider provider protocols with local fixtures. Neither fixture suite establishes hosted deployment or live provider operation.
