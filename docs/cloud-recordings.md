# Private audio attachments

Watson can attach one existing audio file to an owned, uploaded session. Open the session's Audio tab or Settings → Sync & sharing → Private audio attachment. Sign in, explicitly upload the session, and refresh audio info. The server reports whether encrypted storage is configured, its file size limit, supported formats and the effective organization recording policy. Unsupported or unavailable storage disables upload controls.

Choose audio file opens the native file chooser. Only the filename, format, size and selection revision reach the renderer. Confirm that the participants permit upload, then review the destination account, session and file before approving upload or replacement. Changing the selection clears permission. Recording policy revocation closes an open review. Live capture, audio tests and generation block attachment mutations. Capture does not automatically upload audio.

Upload streams binary chunks from the main process to the owner-only recording endpoint; it does not put base64 audio through renderer IPC or the JSON sync body. Source size, modification time and file identity are checked again after approval. The client captures account, server and device identity when an operation is invoked, before joining its request queue. A queued account switch rejects the operation before opening a file or making a recording request. Participant permission, current revision, ownership, storage configuration and policy are enforced by the server as well.

Export audio opens a native save dialog and streams the attachment into a private temporary file. The client verifies the exact byte count and SHA-256 before replacing the chosen destination. Failed or interrupted exports remove the temporary file. Existing inline owner audio can be exported even before encrypted upload storage is configured; its metadata is labeled as legacy inline storage. Delete attachment has a separate confirmation. Disabling stored audio in organization policy removes existing server attachments and blocks new uploads. Refresh clears their cached metadata; confirmed owner deletion remains a valid cleanup operation even if the file has already been removed. Upload and deletion update the session revision and reconcile a download-only workspace response; they do not submit pending personal uploads. Public note links and other accounts cannot read attached audio. Attachment bytes, local paths and provider credentials are absent from `CloudStatus` and ordinary workspace sync.

The local HTTP/SQLite tests use synthetic WAV files larger than 5 MiB and an AES secret-storage fixture. They verify ciphertext does not contain a private marker, exact export bytes, progress, revision refresh, public/foreign exclusion, file changes, policy/configuration/size/MIME checks and queued account changes. The rendered-control fixture verifies permission and final review, selection/policy invalidation, capture guards, metadata-only commands, export and deletion approval, and sign-out. Native broker tests separately inject chooser/save callbacks. These fixtures do not open user files, perform a live upload to a hosted service or establish host OS credential storage behavior.

Run `node --import tsx --test tests/cloud-recordings-client.test.ts tests/recording-broker.test.ts` for the transport/broker checks and `node scripts/check-cloud-recordings-ui.mjs` for the rendered controls. Source hashes and actual outcomes are stored in `evidence/cloud-client-validation.json` and `evidence/cloud-recordings-ui-validation.json`.
